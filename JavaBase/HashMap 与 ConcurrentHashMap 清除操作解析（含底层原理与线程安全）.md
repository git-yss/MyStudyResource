# HashMap 与 ConcurrentHashMap 清除操作解析（含底层原理与线程安全）

在讲解清除操作的区别前，先明确核心结论：**HashMap 是线程不安全的非并发容器，ConcurrentHashMap 是 JDK 专为高并发场景设计的线程安全容器，二者清除操作（清空/删除元素）的底层逻辑、线程安全特性完全不同**。

## 一、先理清核心概念：底层结构与线程安全基础

### 1. HashMap 底层原理（JDK 1.8）

HashMap 核心结构是「数组 + 链表 + 红黑树」：

- 数组（Node[] table）：哈希桶，元素按哈希值定位到对应桶位；

- 链表/红黑树：解决哈希冲突，桶内元素超过 8 个转为红黑树，低于 6 个转回链表；

- 无任何线程安全保障：所有操作（增删改查、清空）均未加锁，多线程操作时会出现数据错乱、死循环（JDK 1.7 头插法，在jdk1.8后采用尾插法可以避免并发时候出现死循环的情况）、元素丢失等问题。

### 2. ConcurrentHashMap 底层原理（JDK 1.8）

ConcurrentHashMap 抛弃了 JDK 1.7 的「分段锁（Segment）」，改用「数组 + 链表 + 红黑树 + CAS + 同步锁（synchronized）」：

- 核心结构和 HashMap 一致（数组+链表+红黑树），但通过「细粒度锁」保障线程安全；

- 锁粒度：锁定**单个哈希桶（桶级锁）**，而非整个容器，并发性能远高于 HashTable（全表锁）；

- 辅助手段：CAS 操作（无锁）处理桶初始化、节点插入等轻量操作，进一步提升并发效率。

## 二、清除操作的具体区别（清空/删除元素）

清除操作分两种场景：**清空整个容器（clear）**、**删除单个元素（remove）**，二者差异如下：

### 1. 清空操作（clear()）

|特性|HashMap|ConcurrentHashMap（JDK 1.8）|
|---|---|---|
|底层逻辑|遍历数组，将所有桶位置为 null|遍历数组，逐个桶位加锁（synchronized），将桶内元素置空|
|线程安全|不安全：多线程清空时可能部分桶未置空，或清空后其他线程插入元素导致数据不一致|安全：但「弱一致性」——清空过程中其他线程仍可读写，最终所有桶会被置空，但遍历过程中可能看到部分未清空的元素|
|性能|快（无锁），但多线程下不可用|并发安全，性能优于 HashTable（细粒度锁）|
### 2. 删除单个元素（remove(key)）

|特性|HashMap|ConcurrentHashMap（JDK 1.8）|
|---|---|---|
|底层逻辑|定位桶位 → 遍历链表/红黑树 → 找到元素后删除，无锁|定位桶位 → 加锁（synchronized）锁定桶节点 → 遍历删除 → 释放锁，全程 CAS 校验|
|线程安全|不安全：多线程删除可能导致链表断裂、元素丢失，或 modCount 不一致触发 ConcurrentModificationException|安全：锁定单个桶，其他桶仍可并发操作，删除过程中不会被其他线程干扰|
|异常风险|多线程遍历删除易抛并发修改异常|弱一致性遍历，不会抛并发修改异常|
#### 核心差异说明

- HashMap 的 remove：直接操作数组/链表，无任何同步措施。比如线程 A 正在删除桶 1 的链表节点，线程 B 同时遍历桶 1，可能导致链表指针错乱，甚至死循环。

- ConcurrentHashMap 的 remove：

    1. 通过哈希值定位到目标桶位；

    2. 用 `synchronized` 锁定该桶的头节点（仅锁定当前桶，不影响其他桶）；

    3. 遍历桶内元素找到目标节点并删除；

    4. 释放锁，同时通过 CAS 更新容器大小；

    5. 整个过程中，其他线程可正常操作其他桶，仅当前桶被短暂锁定，并发效率高。

## 三、ConcurrentHashMap 为什么线程安全？

ConcurrentHashMap 的线程安全并非单一手段，而是「组合拳」，核心保障如下：

### 1. 细粒度锁：桶级锁定（JDK 1.8）

- 摒弃 JDK 1.7 的分段锁（Segment），改用「单个哈希桶」作为锁粒度：

    - 每次只锁定操作的目标桶，而非整个容器；

    - 不同桶的操作可完全并发，仅同一桶的操作串行，大幅提升并发性能。

### 2. CAS 无锁操作：轻量同步

- 对「桶初始化、节点状态更新、大小统计」等轻量操作，使用 CAS（Compare-And-Swap）替代锁：

    - CAS 是硬件级别的原子操作，通过「比较-交换」保证操作的原子性；

    - 比如初始化桶时，多个线程竞争，只有一个线程能通过 CAS 成功初始化，其他线程直接使用已初始化的桶，无锁冲突。

### 3. 不可变的节点设计

- ConcurrentHashMap 的节点（Node）默认是 `final` 修饰的：

    - key 和 hash 值不可修改，避免多线程下元素被篡改；

    - 仅 value 可修改，且修改时需加锁，保证原子性。

### 4. 弱一致性的遍历机制

- 遍历采用「快照式」迭代器，不抛出 ConcurrentModificationException：

    - 遍历过程中，其他线程的修改操作不会影响当前遍历（看到的是遍历开始时的快照）；

    - 保证遍历安全，同时不阻塞写操作。

### 5. 关键操作的原子性保障

- 所有修改操作（增/删/改）均通过「锁 + CAS」保证原子性：

    - 比如删除元素时，先加锁再删除，避免多线程同时修改同一桶；

    - 大小统计（size()）通过 CAS 累加各桶的计数，保证结果准确。
    
    ## ConcurrentHashMap 线程安全的核心关键点：
    
    1. **细粒度锁 + CAS 结合**：空桶用 CAS 无锁插入，非空桶用 `synchronized` 锁定单个桶头节点，既保证安全又减少锁竞争；
    2. **volatile 保证可见性**：数组和节点的核心字段（val、next）用 volatile 修饰，确保多线程间数据即时同步；
    3. **扩容隔离 + 多线程协助**：扩容不阻塞读写，多线程可同时协助扩容，避免单线程扩容的性能瓶颈；
    4. **无锁读操作**：读操作全程无锁，依赖 volatile 保证可见性，兼顾性能和一致性。

## 四、核心区别总结

|维度|HashMap|ConcurrentHashMap|
|---|---|---|
|线程安全|不安全（无任何同步措施）|安全（桶级锁 + CAS + 不可变节点）|
|清除操作锁粒度|无锁|单个哈希桶（细粒度锁）|
|并发修改异常|遍历删除易触发|弱一致性遍历，不触发|
|性能（高并发）|高但数据不安全|并发安全且性能高（仅锁定单个桶）|
|适用场景|单线程/无并发修改的场景|多线程高并发读写的场景|

**HashMap 的核心结构**

JDK 1.8 的 `HashMap` 大概是：

```
数组 + 链表 + 红黑树
```

可以想象成很多个桶：

```
table[0]  -> null
table[1]  -> Node
table[2]  -> Node -> Node -> Node
table[3]  -> TreeNode
table[4]  -> null
```

为什么是数组？

因为数组按下标访问最快。

为什么还要链表？

因为不同 key 可能算出同一个数组下标，这叫**哈希冲突**。

比如：

```
keyA -> hash -> index 5
keyB -> hash -> index 5
```

那 `table[5]` 这个桶里就不止一个元素，只能挂起来。

早期就是链表：

```
table[5] -> A -> B -> C
```

查找时先定位桶，再遍历链表。

------

**为什么链表还要转红黑树？**

如果冲突很少，链表很短，遍历没问题。

但如果很多 key 都落到同一个桶里：

```
table[5] -> A -> B -> C -> D -> E -> F -> G -> H -> I ...
```

查找就从 `O(1)` 退化成 `O(n)`。

这时候 HashMap 就把链表转成红黑树：

```
链表查找：O(n)
红黑树查找：O(log n)
```

所以红黑树不是为了“炫技”，而是为了防止极端冲突下性能退化。

**为什么不是一开始就用红黑树？**

因为红黑树维护成本比链表高：

- 插入要旋转、变色
- 节点结构更复杂，占内存更多
- 小数据量下不一定比链表快

所以 HashMap 的策略是：

> 冲突不严重时用链表，简单省空间；冲突严重时再转红黑树，保证性能下限。

这就是工程里的典型取舍。

------

**为什么链表长度到 8 才树化？**

JDK 1.8 里，桶中链表长度达到 `8` 时，可能树化。

但注意，不是一定树化。

还要看数组长度是否达到 `64`。

```
链表长度 >= 8 且 table.length >= 64 -> 树化
链表长度 >= 8 但 table.length < 64 -> 优先扩容
```

为什么？

如果数组很小，冲突多可能只是因为桶太少。

比如数组长度只有 `16`，你放了很多数据，冲突很正常。这个时候更合理的是扩容，让元素重新分散，而不是急着树化。

所以：

```
桶太少导致冲突 -> 扩容
hash 真的集中冲突 -> 树化
```

这个设计很聪明。

**HashMap 扩容为什么特别重要？**

扩容大概是：

```
旧数组长度 16 -> 新数组长度 32
```

然后旧元素要重新分布到新数组。

JDK 1.8 有一个很妙的优化：

元素扩容后的位置只有两种可能：

```
原位置
原位置 + oldCap
```

比如旧容量是 `16`，某个元素原来在下标 `5`。

扩容到 `32` 后，它要么还在：

```
5
```

要么去：

```
5 + 16 = 21
```

为什么？

因为容量翻倍后，参与下标计算的二进制位多了一位。

只需要看 hash 在 `oldCap` 对应的那一位是 `0` 还是 `1`：

```
0 -> 留在原位置
1 -> 移到原位置 + oldCap
```

这就避免了重新计算完整 hash，迁移更快。

**ConcurrentHashMap put 流程**

简化版：

```
1. 计算 hash
2. 如果 table 没初始化，先初始化
3. 定位桶
4. 如果桶为空，用 CAS 插入
5. 如果桶不为空：
   - 如果正在扩容，帮忙扩容
   - 否则 synchronized 锁住桶头
   - 在链表或红黑树里插入/更新
6. 判断是否需要树化
7. 更新元素数量
8. 必要时触发扩容
```

重点：

```
空桶用 CAS
非空桶锁桶头
扩容时多线程协助迁移
```

**为什么非空桶还要 synchronized？**

因为链表或红黑树的修改不是一个简单赋值。

比如链表插入要：

```
遍历节点
比较 key
更新 value
或者追加新节点
可能树化
```

这些操作是复合操作，CAS 不适合一次性完成。

所以：

```
空桶：简单赋值 -> CAS
非空桶：复杂修改 -> synchronized
```

这就是设计取舍。



**ConcurrentHashMap 扩容为什么可以多线程帮忙？**

HashMap 扩容是单线程搬迁。

ConcurrentHashMap 数据量大时，如果只有一个线程扩容，会很慢，还会阻塞其他写线程。

所以 JDK 1.8 设计成：

```
一个线程发现需要扩容
其他线程再来操作时，如果发现正在扩容，也一起帮忙搬桶
```

这叫协助扩容。

旧数组中的桶迁移完成后，会放一个特殊节点 `ForwardingNode`。

它表示：

```
这个桶已经搬到新数组了
你去新数组找
```

所以扩容过程中，线程不会乱写旧桶，而是能识别迁移状态。

HashMap 里“头插法改尾插法”主要说的是 **JDK 7 到 JDK 8**，链表节点在扩容迁移时插入新桶的方式变了。

核心原因：**避免多线程并发扩容时形成环形链表，导致死循环**。顺带也让节点顺序更稳定。

JDK 7 扩容时用的是头插法：

```
newTable[i] = e;
e.next = oldHead;
```

它会把原链表顺序反转。比如旧桶里是：

```
A -> B -> C
```

迁移后可能变成：

```
C -> B -> A
```

HashMap 本身不是线程安全的。如果两个线程同时触发 resize，头插法在迁移链表时会不断修改 `next` 指针，并且还会反转链表。两个线程交错执行时，可能出现这种结构：

```
A -> B -> A
```

也就是链表成环。之后执行 `get()`、`put()` 遍历这个桶时，就可能一直绕圈，CPU 飙高。

JDK 8 改成尾插法，并且扩容时利用容量翻倍的特性，把原链表拆成两条链：

```
loHead / loTail
hiHead / hiTail
```

判断节点是留在原位置，还是移动到 `oldIndex + oldCap`：

```
if ((e.hash & oldCap) == 0)
    放到 lo 链
else
    放到 hi 链
```

尾插法的效果是：

```
旧链表: A -> B -> C
新链表: A -> B -> C
```

它保持原有相对顺序，不再反转链表，因此大幅降低了并发 resize 下因为指针交错导致链表成环的风险。

不过要注意一句：**JDK 8 的 HashMap 依然不是线程安全的**。尾插法只是修复/规避了 JDK 7 中一个非常典型的并发扩容死循环问题，并不意味着可以在多线程下安全使用 HashMap。多线程场景应该用：

```
ConcurrentHashMap
```

或者外部加锁。

一句话总结：

> JDK 7 头插法扩容会反转链表，多线程并发 resize 时容易把链表改成环；JDK 8 改为尾插法，保持链表顺序，降低环形链表和死循环风险，同时配合红黑树优化长链表性能。
